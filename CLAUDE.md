# closet-ai: notes for Claude Code

## What this is

A wardrobe app, mobile-first. You photograph an item and the app tells you what to wear it with, or helps you sell it. Everything you photograph ends up in your digital wardrobe, so it fills up as a side effect instead of a chore.

The core feature is "Want / Can": the user drops in one item they want (a Balenciaga jacket from Instagram) and the app finds something similar for less from partner brands and resale, plus what close to it they already own. Its sibling is "Inspiration" (Вдохновение / השראה): looks the user likes, saved from screenshots, shared from Pinterest or picked in onboarding, which teach the app their taste and are rebuilt from their wardrobe. See "Feature boundaries" below (decided 2026-10-21).

First market is Israel (Hebrew + Russian, Yad2 and Facebook groups), then Ukraine and Belarus. Free tier forever, 7-day Pro trial, then subscription via RevenueCat. Stylists will later get access to clients' wardrobes, so sharing is part of the data model from the start. See README.md for the full roadmap.

This is also a learning project. The owner is a frontend engineer (React, React Native) building her backend, TypeScript and AI skills on it, and it is part of her portfolio.

## Current state

- pnpm monorepo (`client`, `server`, `shared`), TypeScript ~6.0 strict everywhere (keep one TypeScript version: two versions make pnpm install `expo` twice), Node 22. pnpm may not be on PATH: use `corepack enable` once, or `corepack pnpm …`.
- `server/` (`@closet-ai/server`): Fastify 5 + Zod (`fastify-type-provider-zod`), Drizzle ORM 0.45 on Postgres 17 with pgvector, health check.
  - Auth: Better Auth (email + password) on `/api/auth/*`, Expo plugin, trusted origin `closetai://` (plus `exp://` in development). Its tables (`user`, `session`, `account`, `verification`) are generated by the Better Auth CLI into `src/db/auth-schema.ts`; don't edit that file by hand.
  - Items: `GET/POST /api/items`, `GET/PATCH/DELETE /api/items/:id` require a session (`requireUser` preHandler, 401 otherwise) and only touch the caller's items (`items.owner_id` → `user.id`). Someone else's item answers 404, like a missing one. `GET /api/items/:id` and `PATCH` (name, category, colors, seasons; only the fields sent change) return `itemDetail`: the item plus its photo's `tags`. DELETE removes the row first, then the photo file; a storage failure after that is logged and still answers 204.
  - `buildApp` takes auth, the repositories, the photo queue and storage as parameters, so tests use Better Auth's in-memory adapter, in-memory repos (`createInMemoryRepositories` in `test/helpers.ts`) and a manual queue (`createManualPhotoQueue`, whose `runAll` plays the worker) and need neither a database nor Redis. `disableOriginCheck: false` is set on purpose: Better Auth skips the origin check when NODE_ENV is test.
  - Photos: `POST /api/photos` (multipart, one file, 10 MB cap) checks the header (JPEG/PNG/WebP only, 415 otherwise; sharp's prebuilt binaries can't decode HEIC, so the app converts to JPEG first), stores the original as `uploads/<user id>/<uuid>`, adds a `photos` row (`processing`) and queues a BullMQ job, then answers `{ photoKey, status: "processing" }` at once. The worker (`src/queue/photo-queue.ts`, jobs in `src/modules/photos/photo-jobs.ts`) re-encodes with `sharp` to WebP, at most 2.6 MP (capped by area, not the long side, so a tall phone screenshot keeps ~1100 px of width for full-width covers), quality 85 (1024 px at 70 looked soft; vision models get a 1024 px copy, `modelCopy`, so tagging costs the same), no metadata (EXIF/GPS dropped), stores it at `photoKey` = `photos/<user id>/<uuid>.webp`, marks the row `ready` and deletes the original; 3 attempts with backoff, a non-image is marked `failed` straight away. The worker runs inside the API process for now (`src/server.ts`) and needs `REDIS_URL`. `POST /api/items` takes that `photoKey` (a `photos` row of the caller's, not `failed`; it may still be processing). Items return `photoStatus`, and `photoUrl` = `/api/items/:id/photo` once ready, served by the API to the owner only with `Cache-Control: private, immutable`; the closet re-fetches every 1.5 s while a photo is processing. An hourly cleanup job deletes photos no item points to after a day (abandoned forms, and retries of failed deletes). Deleting an item deletes its photo, original included. Storage is behind the `Storage` interface (`src/storage/storage.ts`): S3 via `@aws-sdk/client-s3` (SeaweedFS locally, Cloudflare R2 in production), in-memory in tests. In development the server creates the bucket on start.
  - Tagging (roadmap step 4): after processing, the worker queues a `tag` job that sends the WebP to Claude Haiku 5.5 (`src/ai/item-tagger.ts`, the one module that calls the model; tests use `createStubTagger`) and stores the answer, validated with structured outputs, in `photos.tags` (`itemTags` in shared: name in the user's language, category, colors, seasons, and fit, length, fabric, style, brand, condition in English for search; `recognized: false` when the photo shows no single item). `POST /api/photos?lang=en|he|ru` sets the name's language; `GET /api/photos/status?key=` returns `{ status, tagStatus, tags }` to the owner only. A refusal is final, other errors retry 3 times. Without `ANTHROPIC_API_KEY` tagging is off (`tagStatus` null) and everything else works. The SDK's `zodOutputFormat` needs Zod 4, so the model's schema is written with `zod/v4` next to the tagger, and a type check fails the build if it drifts from `itemTags`. About $0.0006 and 4–6 s a photo.
  - Embeddings (roadmap step 5): the worker also queues an `embed` job that runs Marqo-FashionSigLIP (Apache 2.0, a SigLIP fine-tuned on fashion) locally through `@huggingface/transformers` / ONNX Runtime (`src/ai/item-embedder.ts`; tests use `createStubEmbedder`) and stores a 768-dim unit vector in `photos.embedding` (pgvector, HNSW cosine index; migration `0005` also enables the `vector` extension). 8-bit weights: ~90 MB, downloaded on first use into `MODEL_CACHE_DIR` (`server/.models`, gitignored), ~70 ms a photo. `GET /api/items/:id/similar` returns up to 6 items of the same category, closest first, with `similarity` (cosine). Same category only, because whole-photo embeddings also see the background. `pnpm --filter @closet-ai/server embeddings:backfill` queues photos that have no embedding yet. Text search is not built: the model's text side only understands English, so queries would need translating first. The model's constants live in `src/ai/embedding-model.ts` so the schema can import them without loading ONNX Runtime.
  - Background removal (roadmap step 8): after processing, a `cutout` job sends the WebP to SAM 3 on fal.ai asking for "garment" (`src/ai/background-remover.ts`; tests use `createStubRemover`), trims the transparent margins, adds 6% padding and stores a transparent WebP at `photos/<user id>/<uuid>-cutout.webp` (`photos.cutout_key`). $0.005 and ~3 s a photo. "Main subject" removers (BiRefNet, Bria) kept the bedspread and feet on the owner's test photos; SAM 3 asked for the garment by name didn't (comparison script in `~/Desktop/closet/wrinkle-lab`). Photo and result travel as data URIs with `sync_mode`, so nothing lands in fal's public storage or request history. Items get `cutoutUrl` = `/api/items/:id/photo?variant=cutout` (its own URL, so the cached photo stays valid). The cut-out waits for the tags: Haiku also answers `onPerson` (not stored), and an item photo where someone wears or holds the item (a selfie, an outfit screenshot) isn't cut out, since the cut-out loses the head and arms around it and looks odd; making that nice is Premium. If tagging gives up, or is off, the photo is cut out as usual. With a remover the `embed` job waits for the cut-out and embeds it flattened on white; if no garment is found, or the job gives up, the photo is embedded as it is. Without `FAL_KEY` nothing is cut out and embedding follows processing as before. `pnpm --filter @closet-ai/server cutouts:backfill` queues ready photos without a cut-out (and re-embeds them). Shoes and bags: "garment" finds nothing on them (owner's photos, 2026-10-21), so tags carry an English `noun` without colour ("ankle boots", "shoulder bag") and `cutOutByName` asks a few ways until one works: clothes "garment", then the noun, then its last word; shoes and bags the noun, its last word, then "shoes" / "bag"; a crop from a look by its noun first. Shoes ask SAM 3 for several masks and keep every one scoring within 75% of the best and at least 30% of the biggest's area, so both shoes of a pair are cut out and bits of the neighbouring pair are not (`applyMasks` builds raw RGBA: sharp runs removeAlpha after joinChannel). A photo without a noun is tagged again for it when cut out. A redone cut-out gets a new key, and cut-out URLs are versioned by their own key, so phones don't keep the old one. Low-contrast photos (a beige skirt on a lilac bed) still fail: retake them.
  - Items from a selfie: `POST /api/photos?kind=look` uploads a whole outfit (`photos.kind`, migration `0007`). It is processed like any photo, then the `tag` job asks Haiku for every item worn or carried (`ItemTagger.findItems`: the item tags plus a relative box, clamped to 0..1) into `photos.look_items`; no cut-out and no embedding for the look itself. `GET /api/photos/status` returns them as `lookItems`. `POST /api/photos/look-items` (`src/modules/photos/look-items.ts`) takes the picked indexes with the user's name, category, colors and seasons, crops the look to each box (+3% margin) into a photo of its own (`createReady`, tags from the look), creates the items and queues their embeddings; crops are not cut out, since they show the person wearing the item. The look stays unattached and the hourly cleanup removes it. About 12 s and ~$0.002 for a selfie with 6 items.
  - Want / Can (roadmap step 7, wardrobe part): `POST /api/photos?kind=want` uploads a screenshot of someone else's look. The `tag` job finds its items like a selfie's, then `matchLookItems` (`src/modules/photos/want-matches.ts`) crops each item, cuts it out with SAM 3 (the crop if that fails), embeds it, takes the 3 closest wardrobe items of the same category (`PhotosRepository.closestItems`, pgvector) and asks Haiku (`ItemTagger.compare`, thumbnails of the crop and the candidates) whether one is the same item, could stand in for it, or neither; stored per item in `photos.matches` (migration `0008`) and returned by `GET /api/photos/status` as `matches` with the wardrobe item (a deleted one reads as none). The model has the last word because the embedding alone can't separate a match from a near miss (prototype on the owner's 5 screenshots: an olive jacket scored 0.79 against a pink shirt, a real match 0.85; scripts in `~/Desktop/closet/wrinkle-lab/want-can`). About 10–20 s and ~$0.01 a screenshot (one comparison per item). Brand options are not built yet.
  - Turning a photo: `POST /api/items/:id/rotate` turns the item's WebP and its cut-out a quarter clockwise with sharp, stores them under a new key (`PhotosRepository.copyAs` copies the row with tags and embedding), points the item at it, deletes the old photo and queues a fresh embedding. Photo URLs carry `?v=` from the storage key (`photoPath`), so a turned photo gets a new URL and the phone's immutable cache doesn't show the old one. A cut-out still being made for the old key is lost (the turned photo then has none).
  - Free-tier limits (decided 2026-10-21; everyone is on the free tier until Pro exists, the owner included): numbers in `shared/src/limits.ts` (5 "want" screenshots and 3 selfies a month, 100 item photos a day as a safety cap). The wardrobe itself is unlimited: an item costs under a cent once and outfits need a full wardrobe, so Pro is sold on the per-use AI features. Each counted upload adds a row to `usage_events` (migration `0009`, with its estimated cost); `src/modules/usage/limits.ts` checks before the action and records after it, periods are calendar UTC (day, Monday week, month). A used-up limit answers 429 with the message `limit:<code>` (`limitCodeOf` in shared). `AI_DAILY_BUDGET_USD` (default 3) is the server's daily stop on estimated spend for everyone. `GET /api/usage` returns what's used. Not yet per device (step 13).
  - "What do I wear this with?" (roadmap step 10, wardrobe items for now): `POST /api/wear-with?lang=` with an `itemId` answers 202 with a request id, or 200 with the last request for that item while the wardrobe has the same number of ready items (asking again is free). An `outfits` BullMQ queue of its own (`src/queue/outfit-queue.ts`, jobs in `src/modules/outfits/outfit-jobs.ts`) composes 4 outfits: `pickCandidates` (`wardrobe-sheet.ts`) keeps in-season pieces and, per category, the ones whose embeddings are closest to the item (≤29, so the prompt doesn't grow with the wardrobe), `contactSheet` draws them numbered, and `src/ai/stylist.ts` (the one module that asks for outfits; tests use `createStubStylist`) sends Haiku the whole wardrobe list and the user's brief as a cached prefix (`cache_control`), then the item and the sheet. Numbers the model makes up are dropped. Stored in `outfit_requests`, `outfits`, `outfit_pieces` (a wardrobe item, the hero, or later a partner `catalog_item_id` with `sponsored`; a deleted item leaves the outfit without that piece) and `outfit_reactions` (like / dislike / none as an opinion, the latest wins; every "wore" counts) — migration `0010`. `GET /api/wear-with/:id` to poll, `POST /api/outfits/:id/reactions`. The style brief (`style_briefs`, one per user) is written by Opus through the Batch API (half price, `brief` job submits, `brief-check` polls every 2 minutes, gives up after a day) from the wardrobe sheets, saved "want" screenshots and reacted outfits, once there are 8+ ready items and when it is stale (±5 items, +5 reactions, or a month); without it the stylist reads taste from the wardrobe. For an item from a photo (a screenshot of something the user doesn't own yet): upload it as `kind=wear` (counted as a photo; the day's outfit limit is checked first), the tag job finds its items like a selfie's (each with an English `noun`, "leather midi skirt", that SAM 3 is asked for instead of "garment"; want looks use it too), then `POST /api/wear-with` with `{ photoKey, index }` crops the picked item into a photo of its own (`outfit_requests.hero_photo_key`, migration `0011`; the hourly cleanup keeps photos a request points to) and the job cuts it out by name and embeds it. Its picture is served at `/api/wear-with/:id/photo` (`?variant=cutout`), the hero pieces show it, and `addable` is what `POST /api/items` needs to add it to the wardrobe (null once an item uses the photo). Limit 5 a day, hidden cap 80 a month (~$1 for the most active free user at ~1.3 ¢ a request). Without `ANTHROPIC_API_KEY` the route answers 503. "Want" screenshots are still deleted by the hourly cleanup after a day, so the brief rarely sees any until Inspiration keeps them.
  - Inspiration (decided 2026-10-21; the first part of "Feature boundaries"): `POST /api/photos?kind=inspiration` saves a look the user likes. It is only processed (no tagging, no cut-out, so saving is free; cap 50 a day) and the hourly cleanup leaves it until `DELETE /api/inspiration?key=`; `GET /api/inspiration` lists them newest first with `/api/inspiration/photo?key=` URLs. Each save (and delete) queues the brief job 2 minutes later, so a few saves go into one brief; the brief is stale after ±3 saved looks and reads the newest 12 (with "want" screenshots still around), weighing the newest most. `POST /api/wear-with` takes an optional `mood` (everyday, office, evening, sporty, surprise; `outfit_requests.mood`, migration `0013`): every look keeps to it, the directions vary them within it, and a reused request must have the same mood (the app's `MoodChips` above the button; none chosen means any). The contact sheet mixes closeness to the item with pieces unlike each other (maximal marginal relevance), no piece goes into more than two looks, and the second look recreates one of the brief's saved looks. Outfits now go in four directions: her core style, the spirit of her saved looks, a step out of her comfort zone, an unexpected mix (migration `0012`).
  - Throw `httpError(status, message)` (`src/http-error.ts`) for 4xx from handlers instead of `reply.code()`: the Zod type provider only allows the statuses in the response schema.
  - Migrations are committed in `server/drizzle/`. `drizzle-kit generate` asks interactively when a column is renamed; generate a drop and an add separately and merge them into one migration (see `0001_photo_key`).

On the owner's Mac Docker runs in OrbStack.

Root `eslint.config.js` covers `server` and `shared` with type-aware `typescript-eslint` rules; `client/eslint.config.js` uses `eslint-config-expo`, which includes the React Compiler rules. `pnpm lint` runs both and fails on warnings.

Commit `pnpm-lock.yaml` together with any `package.json` change.

## Tests

Tests stay inside each package, not in a shared top-level folder:

- `server/test/` for API tests (Vitest). Unit tests for a single module can also sit next to it as `*.test.ts`.
  - `server/test/postgres.test.ts` runs the real app (Drizzle repository, Better Auth Drizzle adapter, committed migrations) on Postgres. It runs only when `TEST_DATABASE_URL` is set, always in CI (a Postgres service in the workflow), and fails in CI if the variable is missing. It wipes that database first, so the database name must end in `_test`. Locally (`pnpm db:up` creates `closet_test`): `TEST_DATABASE_URL=postgres://closet:closet@localhost:5432/closet_test pnpm --filter @closet-ai/server test`.
  - `server/test/storage.test.ts` does the same for S3 storage with `TEST_S3_ENDPOINT` (`http://localhost:8333` locally; CI starts a SeaweedFS container). Shared test setup lives in `server/test/helpers.ts`.
- `client/` uses Jest (jest-expo), with tests next to components as `*.test.tsx`. Never put tests in `src/app`: every file there becomes a route.
- `shared/` gets Vitest only when there's real logic there; plain schemas don't need tests.

Reason: server and client use different test runners and environments (Node vs React Native), and each package should be testable on its own with `pnpm --filter <pkg> test`. If we add end-to-end tests later, they go in a top-level `e2e/`.

## RTL

- RTL is enabled with `supportsRTL: true` in the `expo-localization` plugin (`app.json`); on iOS it only applies to locales listed in `supportedLocales` (en, he, ru).
- Use `start`/`end` (`marginStart`, `paddingEnd`, …) instead of `left`/`right` in styles.
- `textAlign` has no `start`/`end` in React Native: `'left'` follows the layout direction and acts as start.
- Changing direction at runtime (`I18nManager`) needs an app restart and does not work in Expo Go.

Items from a mirror selfie (tried 2026-10-19 on the owner's 7 selfies, scripts `mirror.mjs`, `cheap.mjs`, `boxes.mjs` in `~/Desktop/closet/wrinkle-lab`):

- Cheaper redraws ($0.02: FLUX Kontext dev, FLUX.2, Qwen Edit Plus) changed the items too often (a top became a dress, colours and logos invented). Stay with Nano Banana; rerun `cheap.mjs` when new models come out.

## Outfit taste: how the AI learns to put good outfits together

No model training to start with: the taste comes from the prompt, from examples and from feedback, in this order. For now the owner is the stylist; an outside stylist comes with the stylist feature (step 9).

1. **Style guide in the prompt.** The owner fills in the stylist questionnaire ([doc](https://claude.ai/code/artifact/080bdeac-3673-4e9d-b3de-ea1d20a20bf8): colour, proportions, fabrics, occasions, weather, shoes and accessories, taboos, 10–20 example outfits, the 1–5 scale). Its answers become the style guide the outfit prompts are built on, kept in the repo next to the prompt.
2. **Reference outfits.** The owner's example outfits (and ones she picks, with permission) are embedded and stored; before composing, the closest references are retrieved with pgvector and shown to the model as the direction to follow. Taste changes by editing the library, not by retraining.
3. **Feedback.** Suggested outfits and reactions are stored from step 10 on. First as statistics (which combinations land); with a few thousand rated outfits, a small ranker on the embeddings picks the best of several AI suggestions and adapts to each user.
4. **Evals.** The owner scores the first 30–50 AI outfits on the questionnaire's 1–5 scale with a line on what is off; that set is rerun after every prompt change (step 14), and the "what is off" lines feed new rules and taboos.
5. **Fine-tuning** an open vision model only if 1–4 stop being enough, and only once thousands of rated outfits exist.

## Feature boundaries (decided 2026-10-21)

| | Input | What the user gets |
|---|---|---|
| **Want / Can** (Хочу / Могу) | One item they want: a screenshot or a link (a Balenciaga jacket) | Similar for less from partner brands and resale; the closest piece they already own; later, what to sell to afford the original |
| **Inspiration** (Вдохновение) | Whole looks they like: screenshots, Pinterest via the share sheet, onboarding style cards | The look rebuilt from their wardrobe, what's missing for it, and their taste profile |
| **My style** (Мой стиль) | Everything above plus reactions to outfits | A readable taste summary (the Opus brief), used by outfits and every recommendation |
| **Outfits** (Образы) | The wardrobe + My style | Outfits to wear, with like / not mine / wore it |

- What is built today as the Want tab (look screenshot → items → wardrobe matches) is the first version of Inspiration; it moves there when Want / Can is rebuilt for a single item.
- Taste is per person, never global: one user's likes never shape another user's outfits.
- Onboarding style cards are images we generate once (an image model) and store as static assets shown to every user; never Pinterest or other people's photos (copyright, Pinterest's terms). A user's own screenshots are fine: they are for their private use only and never shown to anyone else.

Outfit prototype (owner's wardrobe, `~/Desktop/closet/wrinkle-lab/outfits`): a plain prompt gives correct but dull outfits; a stylist prompt (hero piece, colour story, proportions, draft many, keep the best) with Opus is much better. The design to build: Opus writes the user's brief (taste from Inspiration, liked outfits and the wardrobe; hero pieces, pairings, traps, wardrobe gaps) when those change (~10 ¢), Haiku composes outfits from the brief per request (a few cents; keep its effort low).

## Partner items in recommendations (decided 2026-10-21)

Brands will pay to have their items shown. Every feature that recommends is built so a partner item can appear in it from the start, with these rules:

- **Separate catalog.** Partner items live in their own catalog (brand = organization from the brand portal, price, link, photos, embedding, status), never in anyone's wardrobe. A user's item only becomes "theirs" if they buy it and add it.
- **Where they can appear:** Want / Can results (the main place); "what's missing" for an Inspiration look; one optional slot in an outfit ("finish it with…"), only when the wardrobe has no good piece for that slot; wardrobe gaps from My style ("black straight trousers would unlock 5 of your saved looks").
- **Relevance first.** Candidates are ranked by fit to the item, look or taste; payment only boosts among items that already fit, and never outranks a clearly better match or a piece the user owns. At most one partner item per outfit, and not in every outfit.
- **Always labelled** as a partner item / ad in the UI, in every language.
- **Data model:** a stored outfit's pieces reference either a wardrobe item or a catalog item (one of two nullable columns plus the slot), with a `sponsored` flag, so outfits with partner pieces need no rewrite later.
- **Measured per impression:** shown, opened, clicked through, saved, bought (when the brand reports it), for the brand dashboard. Brands see aggregates only, never who the user is or their wardrobe and taste profile.
- Free and Premium both see partner items (partners pay for reach); Premium may later get fewer.

## "Want / Can": look screenshot → what you have, what you can buy

> Written before the 2026-10-21 split: the look-screenshot flow below is now Inspiration, and Want / Can takes a single item (see "Feature boundaries"). The steps and rules still hold for Inspiration.

The user drops in a screenshot of a look they like (Pinterest, Instagram, a photo). The app splits it into items and rebuilds the look from the user's wardrobe and partner brands.

Flow:

1. Upload the screenshot through the existing photo pipeline (`POST /api/photos`). It is processed as a background job like other AI work.
2. A vision model returns the items it sees, validated with a Zod schema in `shared`: for each item `category`, `color`, `cut`/`silhouette`, `length`, `fabric`, `style`, a short description, a bounding box (relative 0–1 coords) and a `confidence`. Items that are cut off or hidden are returned with low confidence or skipped; never guess.
3. For each item, crop the screenshot by its box and search by image embedding plus text description (pgvector):
   - first the user's own wardrobe (`source = own`);
   - then partner brands (`brand_partner`); until partners exist, use the demo live search below behind the same interface;
   - later resale.
4. Result per item: `owned` (best match from the wardrobe, similarity score), `buy` (up to 3 brand items with price and link), or `missing` (nothing close enough). Thresholds live in one config so they can be tuned.
5. Summary for the whole look: how many items the user already has ("3 of 5 from your wardrobe") and the rough cost of the rest.

UI (client): screenshot at the top with item boxes, then one row per item: the detected item, the user's match or the brand options, and an honest "couldn't make out the shoes" when confidence is low. A "save as outfit" action and a share card ("I rebuilt this Pinterest look from my wardrobe") for the videos.

Rules:
- Results from brands are labelled as partner items once real partners exist; a brand never outranks a clearly better match.
- Counts against the free-tier AI limits (one screenshot = one action, whatever the number of items).

Free and Premium (decided 2026-10-19):

| | Free | Premium |
|---|---|---|
| Look screenshots | 3–5 per month | unlimited |
| Matches from the user's wardrobe | yes | yes |
| Partner brand options | yes | yes |
| Save the look as an outfit, history of looks | no | yes |
| "Sell what you don't wear to afford it" (listing on Yad2) | no | yes |
| Price comparison and sale alerts | no | yes |

Why not Premium-only: Want / Can is what a new user tries first and what the share cards spread, so a paywall at the first screenshot loses people before they see it work. A free look costs about $0.01 (vision model to find and compare the items + our own pgvector search). Brand options stay free because partners pay for impressions and clicks: hiding them would shrink what we can offer partners. The limit is set by value, not cost: users hit it once the feature is a habit, which is when the trial and the subscription are offered.

Cost (estimates, October 2026; check before committing): recognising the items in a screenshot is ~$0.001 on Claude Haiku 5.5, and comparing each with its wardrobe candidates another ~$0.002 an item (~$0.01 a screenshot as built) (compare with Gemini Flash on the eval set, mainly for box accuracy); wardrobe and partner-catalog search run on our own Postgres. The live brand search below (~$5–8 per 1,000 searches) is the only expensive part, and it is demo-only.
- The screenshot belongs to the user's private use; don't publish or reuse it anywhere.
- Add 15–20 real look screenshots with hand-written expected items to the eval set.

## Demo: brand recommendations via live search (for pitching brands)

Goal: show brands and partners how the app recommends their items, before any partner has given us a catalog. This is a demo feature, not the production design.

How it works:

1. A config file holds a plain list of brand sites: `server/src/modules/showroom/demo-sites.ts` exporting `DEMO_SITES: { name: string; url: string; instagram?: string }[]`. Order matters: the first sites are searched first, so before a meeting with a specific brand we move that brand to the top.
2. Input: a user item or one item cropped from a "Want / Can" look screenshot. The vision model turns it into a short search description (type, colour, cut, length, fabric), validated with a Zod schema.
3. Search only within the listed domains through a web search API that supports domain filtering (pick one, explain the choice and the cost per request). No crawling, no storing the sites' catalogs, no Instagram scraping.
4. The model looks at the found product pages and returns the 3-5 closest items: title, price if shown, image URL, product URL, brand name, and a one-line reason why it matches.
5. Every result links to the brand's own site.
6. Cache results per query for a day so the demo is fast and cheap.
7. Behind a feature flag (`SHOWROOM_SOURCE=demo-search | partners-db`). Partners-db is the future mode where we search our own stored catalog of brands that agreed. Switching must not touch the client.

Also for the demo: a simple "Brand dashboard" screen (web, can be static data for now) showing impressions, clicks to the brand's site, and the user queries that surfaced their items.

Rules:
- Demo only: not shown in public builds, store screenshots or marketing until the brand has agreed.
- Low request volume, respect robots.txt, remove a brand immediately if they ask.
- Results labelled as partner/ads in the UI once real partners exist.

## Conventions

- Zod schema in `shared` is the single source of truth: TS types, request validation and DB enums (category, season, color) come from it.
- AI calls go through one client module in `server` so tests can swap it for a stub and never spend money.
- Secrets only in `.env`, never committed. `.env.example` is kept up to date.
- UI strings go through i18n from the start (en as fallback, he, ru; uk later). No hardcoded text in components. New strings go into `en.json` first; a test checks that he and ru have the same keys. Russian copy addresses the user as «ты» (as in the design), never «вы».
