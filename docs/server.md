# Server (`server/`) and shared (`shared/`)

How the server works, module by module. Read the part you are changing; CLAUDE.md has the rules.

`server/` (`@closet-ai/server`): Fastify 5 + Zod (`fastify-type-provider-zod`), Drizzle ORM 0.45 on Postgres 17 with pgvector, health check.

- Auth: Better Auth (email + password) on `/api/auth/*`, Expo plugin, trusted origin `closetai://` (plus `exp://` in development). Its tables (`user`, `session`, `account`, `verification`) are generated by the Better Auth CLI into `src/db/auth-schema.ts`; don't edit that file by hand.
- Items: `GET/POST /api/items`, `GET/PATCH/DELETE /api/items/:id` require a session (`requireUser` preHandler, 401 otherwise) and only touch the caller's items (`items.owner_id` → `user.id`). Someone else's item answers 404, like a missing one. `GET /api/items/:id` and `PATCH` (name, category, colors, seasons; only the fields sent change) return `itemDetail`: the item plus its photo's `tags`. DELETE removes the row first, then the photo file; a storage failure after that is logged and still answers 204.
- `buildApp` takes auth, the repositories, the photo queue and storage as parameters, so tests use Better Auth's in-memory adapter, in-memory repos (`createInMemoryRepositories` in `test/helpers.ts`) and a manual queue (`createManualPhotoQueue`, whose `runAll` plays the worker) and need neither a database nor Redis. `disableOriginCheck: false` is set on purpose: Better Auth skips the origin check when NODE_ENV is test.
- Photos: `POST /api/photos` (multipart, one file, 10 MB cap) checks the header (JPEG/PNG/WebP only, 415 otherwise; sharp's prebuilt binaries can't decode HEIC, so the app converts to JPEG first), stores the original as `uploads/<user id>/<uuid>`, adds a `photos` row (`processing`) and queues a BullMQ job, then answers `{ photoKey, status: "processing" }` at once. The worker (`src/queue/photo-queue.ts`, jobs in `src/modules/photos/photo-jobs.ts`) re-encodes with `sharp` to WebP, at most 2.6 MP (capped by area, not the long side, so a tall phone screenshot keeps ~1100 px of width for full-width covers), quality 85 (1024 px at 70 looked soft; vision models get a 1024 px copy, `modelCopy`, so tagging costs the same), no metadata (EXIF/GPS dropped), stores it at `photoKey` = `photos/<user id>/<uuid>.webp`, marks the row `ready` and deletes the original; 3 attempts with backoff, a non-image is marked `failed` straight away. The workers (`src/workers.ts`) run inside the API process when `WORKERS_IN_API` is true (the default, one command locally) or in their own process (`src/worker.ts`, `dev:worker` / `start:worker`; production sets `WORKERS_IN_API=false`); they need `REDIS_URL`, the database and storage. Measured 2026-10-22 on an M2 (`bench:worker`): API alone ~150 MB; worker ~470 MB once the embedding model is loaded, ~570 MB peak at concurrency 4; ~0.75 s of CPU a photo (sharp ~0.3 s, copies ~0.15 s, embedding ~0.08 s), expect 2–3× on a shared cloud vCPU. `POST /api/items` takes that `photoKey` (a `photos` row of the caller's, not `failed`; it may still be processing). Items return `photoStatus`, and `photoUrl` = `/api/items/:id/photo` once ready, served by the API to the owner only with `Cache-Control: private, immutable`; the closet re-fetches every 1.5 s while a photo is processing. An hourly cleanup job deletes photos no item points to after a day (abandoned forms, and retries of failed deletes). Deleting an item deletes its photo, original included. Storage is behind the `Storage` interface (`src/storage/storage.ts`): S3 via `@aws-sdk/client-s3` (SeaweedFS locally, Cloudflare R2 in production), in-memory in tests. In development the server creates the bucket on start.
- Tagging (roadmap step 4): after processing, the worker queues a `tag` job that sends the WebP to Claude Haiku 5.5 (`src/ai/item-tagger.ts`, the one module that calls the model; tests use `createStubTagger`) and stores the answer, validated with structured outputs, in `photos.tags` (`itemTags` in shared: name in the user's language, category, colors, seasons, and fit, length, fabric, style, brand, condition in English for search; `recognized: false` when the photo shows no single item). `POST /api/photos?lang=en|he|ru` sets the name's language; `GET /api/photos/status?key=` returns `{ status, tagStatus, tags }` to the owner only. A refusal is final, other errors retry 3 times. Without `ANTHROPIC_API_KEY` tagging is off (`tagStatus` null) and everything else works. The SDK's `zodOutputFormat` needs Zod 4, so the model's schema is written with `zod/v4` next to the tagger, and a type check fails the build if it drifts from `itemTags`. About $0.0006 and 4–6 s a photo.
- Embeddings (roadmap step 5): the worker also queues an `embed` job that runs Marqo-FashionSigLIP (Apache 2.0, a SigLIP fine-tuned on fashion) locally through `@huggingface/transformers` / ONNX Runtime (`src/ai/item-embedder.ts`; tests use `createStubEmbedder`) and stores a 768-dim unit vector in `photos.embedding` (pgvector, HNSW cosine index; migration `0005` also enables the `vector` extension). 8-bit weights: ~90 MB, downloaded on first use into `MODEL_CACHE_DIR` (`server/.models`, gitignored), ~70 ms a photo. `GET /api/items/:id/similar` returns up to 6 items of the same category, closest first, with `similarity` (cosine). Same category only, because whole-photo embeddings also see the background. `pnpm --filter @closet-ai/server embeddings:backfill` queues photos that have no embedding yet. Text search is not built: the model's text side only understands English, so queries would need translating first. The model's constants live in `src/ai/embedding-model.ts` so the schema can import them without loading ONNX Runtime.
- Background removal (roadmap step 8): after processing, a `cutout` job sends the WebP to SAM 3 on fal.ai asking for "garment" (`src/ai/background-remover.ts`; tests use `createStubRemover`), trims the transparent margins, adds 6% padding and stores a transparent WebP at `photos/<user id>/<uuid>-cutout.webp` (`photos.cutout_key`). $0.005 and ~3 s a photo. "Main subject" removers (BiRefNet, Bria) kept the bedspread and feet on the owner's test photos; SAM 3 asked for the garment by name didn't (comparison script in `~/Desktop/closet/wrinkle-lab`). Photo and result travel as data URIs with `sync_mode`, so nothing lands in fal's public storage or request history. Items get `cutoutUrl` = `/api/items/:id/photo?variant=cutout` (its own URL, so the cached photo stays valid). The cut-out waits for the tags: Haiku also answers `onPerson` (not stored), and an item photo where someone wears or holds the item (a selfie, an outfit screenshot) isn't cut out, since the cut-out loses the head and arms around it and looks odd; making that nice is Premium. If tagging gives up, or is off, the photo is cut out as usual. With a remover the `embed` job waits for the cut-out and embeds it flattened on white; if no garment is found, or the job gives up, the photo is embedded as it is. Without `FAL_KEY` nothing is cut out and embedding follows processing as before. `pnpm --filter @closet-ai/server cutouts:backfill` queues ready photos without a cut-out (and re-embeds them). Shoes and bags: "garment" finds nothing on them (owner's photos, 2026-10-21), so tags carry an English `noun` without colour ("ankle boots", "shoulder bag") and `cutOutByName` asks a few ways until one works: clothes "garment", then the noun, then its last word; shoes and bags the noun, its last word, then "shoes" / "bag"; a crop from a look by its noun first. Shoes ask SAM 3 for several masks and keep every one scoring within 75% of the best and at least 30% of the biggest's area, so both shoes of a pair are cut out and bits of the neighbouring pair are not (`applyMasks` builds raw RGBA: sharp runs removeAlpha after joinChannel). A photo without a noun is tagged again for it when cut out. A redone cut-out gets a new key, and cut-out URLs are versioned by their own key, so phones don't keep the old one. Low-contrast photos (a beige skirt on a lilac bed) still fail: retake them.
- Items from a selfie: `POST /api/photos?kind=look` uploads a whole outfit (`photos.kind`, migration `0007`). It is processed like any photo, then the `tag` job asks Haiku for every item worn or carried (`ItemTagger.findItems`: the item tags plus a relative box, clamped to 0..1) into `photos.look_items`; no cut-out and no embedding for the look itself. `GET /api/photos/status` returns them as `lookItems`. `POST /api/photos/look-items` (`src/modules/photos/look-items.ts`) takes the picked indexes with the user's name, category, colors and seasons, crops the look to each box (+3% margin) into a photo of its own (`createReady`, tags from the look), creates the items and queues their embeddings; crops are not cut out, since they show the person wearing the item. The look stays unattached and the hourly cleanup removes it. About 12 s and ~$0.002 for a selfie with 6 items.
- Want / Can (roadmap step 7, wardrobe part): `POST /api/photos?kind=want` uploads a screenshot of someone else's look. The `tag` job finds its items like a selfie's, then `matchLookItems` (`src/modules/photos/want-matches.ts`) crops each item, cuts it out with SAM 3 (the crop if that fails), embeds it, takes the 3 closest wardrobe items of the same category (`PhotosRepository.closestItems`, pgvector) and asks Haiku (`ItemTagger.compare`, thumbnails of the crop and the candidates) whether one is the same item, could stand in for it, or neither; stored per item in `photos.matches` (migration `0008`) and returned by `GET /api/photos/status` as `matches` with the wardrobe item (a deleted one reads as none). The model has the last word because the embedding alone can't separate a match from a near miss (prototype on the owner's 5 screenshots: an olive jacket scored 0.79 against a pink shirt, a real match 0.85; scripts in `~/Desktop/closet/wrinkle-lab/want-can`). About 10–20 s and ~$0.01 a screenshot (one comparison per item). Brand options are not built yet.
- Turning a photo: `POST /api/items/:id/rotate` turns the item's WebP and its cut-out a quarter clockwise with sharp, stores them under a new key (`PhotosRepository.copyAs` copies the row with tags and embedding), points the item at it, deletes the old photo and queues a fresh embedding. Photo URLs carry `?v=` from the storage key (`photoPath`), so a turned photo gets a new URL and the phone's immutable cache doesn't show the old one. A cut-out still being made for the old key is lost (the turned photo then has none).
- Free-tier limits (decided 2026-10-21; everyone is on the free tier until Pro exists, the owner included): numbers in `shared/src/limits.ts` (5 "want" screenshots and 3 selfies a month, 100 item photos a day as a safety cap). The wardrobe itself is unlimited: an item costs under a cent once and outfits need a full wardrobe, so Pro is sold on the per-use AI features. Each counted upload adds a row to `usage_events` (migration `0009`, with its estimated cost); `src/modules/usage/limits.ts` checks before the action and records after it, periods are calendar UTC (day, Monday week, month). A used-up limit answers 429 with the message `limit:<code>` (`limitCodeOf` in shared). `AI_DAILY_BUDGET_USD` (default 3) is the server's daily stop on estimated spend for everyone. `GET /api/usage` returns what's used. Not yet per device (step 13).
- "What do I wear this with?" (roadmap step 10, wardrobe items for now): `POST /api/wear-with?lang=` with an `itemId` answers 202 with a request id, or 200 with the last request for that item while the wardrobe has the same number of ready items (asking again is free). An `outfits` BullMQ queue of its own (`src/queue/outfit-queue.ts`, jobs in `src/modules/outfits/outfit-jobs.ts`) composes 4 outfits: `pickCandidates` (`wardrobe-sheet.ts`) keeps in-season pieces and, per category, the ones whose embeddings are closest to the item (≤29, so the prompt doesn't grow with the wardrobe), `contactSheet` draws them numbered, and `src/ai/stylist.ts` (the one module that asks for outfits; tests use `createStubStylist`) sends Haiku the whole wardrobe list and the user's brief as a cached prefix (`cache_control`), then the item and the sheet. Numbers the model makes up are dropped; a wardrobe piece it took from the list though not on the sheet is kept (dropping it left a halter top without the skirt "why" spoke of, 2026-10-22), and a look with neither a dress nor a top and a bottom is left out (`isComplete`) unless every look is. Stored in `outfit_requests`, `outfits`, `outfit_pieces` (a wardrobe item, the hero, or later a partner `catalog_item_id` with `sponsored`; a deleted item leaves the outfit without that piece) and `outfit_reactions` (like / dislike / none as an opinion, the latest wins; every "wore" counts) — migration `0010`. `GET /api/wear-with/:id` to poll, `POST /api/outfits/:id/reactions`. The style brief (`style_briefs`, one per user) is written by Opus through the Batch API (half price, `brief` job submits, `brief-check` polls every 2 minutes, gives up after a day) from the wardrobe sheets, saved "want" screenshots and reacted outfits, once there are 8+ ready items and when it is stale (±5 items, +5 reactions, or a month); without it the stylist reads taste from the wardrobe. For an item from a photo (a screenshot of something the user doesn't own yet): upload it as `kind=wear` (counted as a photo; the day's outfit limit is checked first), the tag job finds its items like a selfie's (each with an English `noun`, "leather midi skirt", that SAM 3 is asked for instead of "garment"; want looks use it too), then `POST /api/wear-with` with `{ photoKey, index }` crops the picked item into a photo of its own (`outfit_requests.hero_photo_key`, migration `0011`; the hourly cleanup keeps photos a request points to) and the job cuts it out by name and embeds it. Its picture is served at `/api/wear-with/:id/photo` (`?variant=cutout`), the hero pieces show it, and `addable` is what `POST /api/items` needs to add it to the wardrobe (null once an item uses the photo). Limit 5 a day, hidden cap 80 a month (~$1 for the most active free user at ~1.3 ¢ a request). Without `ANTHROPIC_API_KEY` the route answers 503. "Want" screenshots are still deleted by the hourly cleanup after a day, so the brief rarely sees any until Inspiration keeps them.
- Inspiration (decided 2026-10-21; the first part of "Feature boundaries"): `POST /api/photos?kind=inspiration` saves a look the user likes. It is only processed (no tagging, no cut-out, so saving is free; cap 50 a day) and the hourly cleanup leaves it until `DELETE /api/inspiration?key=`; `GET /api/inspiration` lists them newest first with `/api/inspiration/photo?key=` URLs. Each save (and delete) queues the brief job 2 minutes later, so a few saves go into one brief; the brief is stale after ±3 saved looks and reads the newest 12 (with "want" screenshots still around), weighing the newest most. `POST /api/wear-with` takes an optional `mood` (everyday, office, evening, sporty, surprise; `outfit_requests.mood`, migration `0013`): every look keeps to it, the directions vary them within it, and a reused request must have the same mood (the app's `MoodChips` above the button; none chosen means any). The contact sheet mixes closeness to the item with pieces unlike each other (maximal marginal relevance), no piece goes into more than two looks, and the second look recreates one of the brief's saved looks. Freshness (2026-10-22: the owner's last 32 looks used the same dozen of 61 pieces, the tweed blazer and pink boots in 8–9): `recentlyUsed` counts the pieces of her last 6 requests (`RECENT_REQUESTS`), `pickCandidates` lowers each one's score by 0.05 per recent look (up to 3), and the model gets those sheet pieces with their counts and the recent looks' names, to prefer fresh pieces and new names; the brief's hero pieces are taste, not pieces for every look. Recomposing three of her items: the four favourites in none of 12 looks, 20 different pieces. Verdict (decided 2026-10-22, migration `0017`): for an item from a photo, one she may buy, the same compose call also answers `verdict` (buy / think / skip, one sentence, and `twin`, the owned piece it nearly repeats); the model gets the 3 owned pieces of its category closest by embedding with their cosines, and decides itself, since shape counts more than colour there (her white and grey ribbed tanks score 0.93). Stored in `outfit_requests.verdict` with `twinItemId`, returned by `GET /api/wear-with/:id` with the twin as an item (left out once deleted). Tried on three of her pieces as if not owned: white ribbed tank "think" (repeats the grey one), sequin tweed jacket "think", red knit mini "buy" (no knit mini in the wardrobe). Texts she reads speak to her ("ты"), never with piece numbers. Outfits now go in four directions: her core style, the spirit of her saved looks, a step out of her comfort zone, an unexpected mix (migration `0012`).
- Deleting the account (required by the App Store): Better Auth's `POST /api/auth/delete-user` with the password (`user.deleteUser` in `src/auth/auth.ts`); every table of the user's goes with the `user` row (ON DELETE CASCADE), then `afterDelete` removes their files by prefix (`deleteUserFiles`, `photos/<id>/` and `uploads/<id>/`, `Storage.deletePrefix`; a failure is logged). The app's Profile has "Delete account" (`src/screens/delete-account`: password, then sign-out).
- Brand and price (migration `0014`): items have an optional `brand`, `price` (main units in the API, cents in `items.price_minor`) and `currency` (`CURRENCIES` in shared: ILS, USD, EUR, GBP, RUB, UAH, BYN); a price needs its currency (400 otherwise). The migration fills `brand` from the photo's tags where the model read one; the add-item forms prefill it the same way. The app's fields: `BrandPriceFields`, parsing in `src/lib/price.ts` (a comma works as the decimal point; the default currency is the phone's, else ₪).
- Profile details (decided 2026-10-22, migration `0015`): `profiles` (one row per user, all optional: ISO country, city, birth year (13+), height in cm, `BODY_SHAPES` silhouette, sizes for tops, bottoms and shoes); `GET` / `PATCH /api/profile` (only the fields sent, `null` clears). The name stays on the Better Auth user. The app: Profile → My details (`src/screens/profile-details`). Not used by the stylist or partner items yet.
- Partner catalog (decided 2026-10-22, migration `0016`): `catalog_items` holds brands' items apart from any wardrobe (brand as text until the brand portal, names per language, our category and colours, price in cents, link, a transparent WebP at `catalog/<feed id>.webp`, its embedding flattened on white like wardrobe cut-outs, in stock, `demo` for made-up brands whose links lead nowhere); `outfit_pieces.catalog_item_id` now references it. `pnpm --filter @closet-ai/server catalog:import [folder]` reads `feed.json` plus pictures (default `seed/catalog`: the demo catalog, 100 items of the made-up STUDIO EDIT from the owner's sheet, ~0.9 MB, so a deploy must ship `seed/`), embeds them locally and upserts by feed id (~13 s for 100). `GET /api/catalog?lang=&category=` (the Edit: in stock, ordered by the angle to the average of the user's wardrobe embeddings in one query, feed order without a wardrobe; not counted as shown), `GET /api/catalog/:id?lang=` (any signed-in user; English when the feed has no name in the language) and `/api/catalog/:id/photo`. `catalog_events` counts shown / opened / clicked per item for brands, aggregates only; the card counts as opened. In outfits: `pickShop` (`wardrobe-sheet.ts`) takes the catalog pieces closest to the item in the categories it leaves room for (shoes 3, accessories 3, outerwear, tops, bottoms 2 each, never a dress), on a second contact sheet numbered after the wardrobe; the stylist may put one in a look's `partner` only where the wardrobe has nothing as good, and the job keeps it in at most two looks (`MAX_PARTNER_LOOKS`), drops made-up numbers and the look's `missing` for that slot, stores it as a sponsored `catalog_item_id` piece and counts it shown. `GET /api/wear-with/:id?lang=` returns it as the piece's `catalogItem`. In Want / Can: each look item's embedding also asks the catalog (`want-matches.ts`): up to 3 pieces of its category at cosine ≥ 0.65 (calibrated on the owner's 5 test screenshots: fitting offers 0.68–0.82, unlike ones 0.59–0.64), and for shoes and accessories only the same kind by the last word of the English names (a bag for a bag, not a hat); stored as `shop` ids in `photos.matches`, counted shown, and returned by `GET /api/photos/status?lang=` as each match's `shop`. `PARTNER_ITEMS=false` switches both off. One try on the owner's wardrobe (2026-10-22): boots and loafers in 2 of 4 looks, ~2.6 ¢ a request with the extra sheet.
- Wishes (decided 2026-10-22, migration `0018`): pieces from photos the user wants to buy. `wishes` (one per item-from-a-photo request, `ask_at`, `still_count`); `POST /api/wishes { requestId }` (her own photo request, else 404; saving again returns the same wish), `GET /api/wishes` (due ones first, with the piece's name and picture from the request's photo and the verdict's call), `GET /api/wishes/due` (the menu row's count), `POST /api/wishes/:id/answer { still | no | bought }`: still moves `ask_at` a week on and counts, only once due (409 before, so a retry can't inflate the count), no and bought delete it. A piece from a photo added to the wardrobe (`POST /api/items` with its `photoKey`) lets its wish go, and a piece already in the wardrobe can't be wished for (409). The list reads wishes with their request and photo in one query. `GET /api/wear-with/:id` returns its `wishId`. The week is `WISH_ASK_AFTER_MS`; asking is in the app (a due wish waits on the Wishes screen, its count on the menu row), push notifications come with the builds.
- Throw `httpError(status, message)` (`src/http-error.ts`) for 4xx from handlers instead of `reply.code()`: the Zod type provider only allows the statuses in the response schema.
- Migrations are committed in `server/drizzle/`. `drizzle-kit generate` asks interactively when a column is renamed; generate a drop and an add separately and merge them into one migration (see `0001_photo_key`).

## Shared

`shared/` (`@closet-ai/shared`): Zod schemas and types for server and client. Exported as raw TS (`exports: ./src/index.ts`), no build step.
